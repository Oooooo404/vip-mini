 vip-mini 性能测试报告

 一、测试环境

- CPU: 13th Gen Intel(R) Core(TM) i5-13420H (8核12线程)
- 内存: 16GB LPDDR5
- 靶子系统: FastAPI + MySQL 8.0 (Docker) + Redis 7
- 启动方式: uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4
- 压测工具: JMeter 5.6.3 (命令行模式)
- 测试账号: 200 个 (load001 ~ load200, CSV 参数化)

 二、测试场景

- 接口: POST /api/user/login
- 请求体: {"username": "${username}", "password": "${password}"}
- 断言: 响应码 200 + 响应体包含 "code":0

 四、稳定性测试（优化前）

- 并发数: 70

 五、瓶颈定位

- CPU: 38%，未打满
- 内存: 83%，偏高但未爆
- 磁盘: 活动时间 47%，读写速度很低
- 慢查询日志: 阈值调至 0.1 秒后仍无记录，说明无慢 SQL
- 结论: 瓶颈在 Python 应用层，`db.py` 每次请求都新建 MySQL 连接，开销巨大

 六、优化方案

- 问题: `db.py` 每次调用 `conn()` 都新建一个 MySQL 连接，用完就关。高并发时，连接建立和认证的开销成为瓶颈。
- 方案: 引入 `DBUtils` 连接池 (`PooledDB`)，复用连接，最大连接数 20，初始空闲连接 5。
- 代码: 见 `db.py`

 九、结论

- 优化前峰值 TPS ≈ 16.42/sec，出现在 100 并发左右
- 优化后 100 并发 TPS 达到 397.14/sec，平均响应从 4895ms 降至 39ms
- 瓶颈定位准确：数据库连接创建开销是主要瓶颈
- 连接池优化后，TPS 提升约 24 倍

 十、遇到的问题与解决

- 响应时间飙到 9 秒：靶子系统用 `uvicorn --reload` 开发模式跑，性能极差。→ 改成生产模式 `uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4`，响应时间降至 2.6 秒。
